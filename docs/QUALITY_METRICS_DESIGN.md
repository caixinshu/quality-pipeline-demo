# 质量度量体系设计文档

> 本文档定义了项目质量度量体系，包含过程指标、结果指标和效率指标三类，共 14 个指标。
> 每个指标包含定义、目的、计算公式、目标值、采集方式和采集频率。

---

## 一、设计原则

### 1. 指标成组原则

单一指标容易被操纵，要成组设计相互制衡：

- 只看覆盖率 → 写无意义的 assert 凑数
- 只看 Bug 数 → 开发少报 Bug
- 只看通过率 → 删掉失败的用例

**解法**：覆盖率 + 通过率 + 漏测率 成组使用，互相印证。

### 2. 古德哈特定律

> 当一个指标变成了目标，它就不再是一个好指标。

指标是度量工具，不是考核工具。指标用于发现问题和引导改进，而非惩罚团队。

### 3. 务实原则

- 过程指标和效率指标可从 CI 自动采集，优先实现
- 结果指标（线上 Bug 数等）先设计定义，留空数据位
- 目标值是方向，不是及格线

## 二、过程指标（6 个）

> 过程指标衡量「做得怎么样」，反映研发过程中的质量状况。

| # | 指标名称 | 定义 | 计算公式 | 目标值 | 采集方式 | 频率 |
|---|---------|------|----------|--------|---------|------|
| P1 | 自动化用例通过率 | 自动化用例执行的通过率 | 通过用例数 / 总用例数 × 100% | ≥ 95% | junit XML 解析 | 每次 CI |
| P2 | P0 用例通过率 | 最高优先级用例的通过率 | P0 通过数 / P0 总数 × 100% | 100% | junit + marker | 每次 CI |
| P3 | 代码覆盖率 | 行覆盖率 | 已覆盖行 / 总行数 × 100% | ≥ 70% | pytest-cov | 每次 CI |
| P4 | 门禁阻断率 | 被质量门禁拦住的 PR 比例 | 被阻断 PR 数 / 总 PR 数 × 100% | 5-15% | GitHub API | 每周 |
| P5 | 代码扫描告警数 | 每千行代码的告警数 | 告警数 / 代码行数 × 1000 | 趋势下降 | lint 工具 | 每次 CI |
| P6 | 高危安全问题数 | 安全扫描发现的高危问题 | bandit high severity 数 | 0 | bandit | 每次 CI |

### 指标详解

**P1 自动化用例通过率**
- 目的：监控测试稳定性，通过率突降说明代码引入了回归
- 采集：解析 junit XML 的 `<testsuite>` 标签，读取 tests / failures 属性
- 阈值：< 95% 触发告警；< 90% 阻断流水线

**P2 P0 用例通过率**
- 目的：核心链路必须 100% 通过，任何 P0 失败都是阻断级事件
- 采集：pytest `-m smoke` 标记的用例，从 junit XML 过滤
- 阈值：< 100% 立即阻断

**P3 代码覆盖率**
- 目的：监控测试覆盖范围，覆盖率下降说明新增代码未被测试
- 采集：pytest-cov 生成 coverage.xml，解析 `<line>` 标签
- 阈值：< 70% 阻断；分支覆盖率 < 60% 告警

**P4 门禁阻断率**
- 目的：监控门禁有效性，过高说明质量差，过低说明门禁太松
- 采集：统计 GitHub PR 中 status check 失败的比例
- 阈值：0% 说明门禁形同虚设；> 30% 说明质量严重下降

**P5 代码扫描告警数**
- 目的：监控代码质量趋势，告警数上升说明代码质量下降
- 采集：flake8 `--count` 输出 + pylint 评分
- 阈值：趋势上升触发告警

**P6 高危安全问题数**
- 目的：安全红线，高危问题必须零容忍
- 采集：bandit `-f txt` 报告中 HIGH severity 数量
- 阈值：> 0 阻断流水线

## 三、结果指标（4 个）

> 结果指标衡量「结果好不好」，反映最终交付质量。
> 本项目无真实线上数据，先设计定义，数据位留空。

| # | 指标名称 | 定义 | 计算公式 | 目标值 | 采集方式 | 频率 |
|---|---------|------|----------|--------|---------|------|
| R1 | 线上 Bug 数 | 生产环境发现的 Bug 数量 | 统计周期内线上 Bug 总数 | 趋势下降 | 手动录入 / Bug 系统 | 每月 |
| R2 | 缺陷密度 | 每千行代码的 Bug 数 | Bug 数 / 代码行数 × 1000 | ≤ 2 | 手动计算 | 每月 |
| R3 | 漏测率 | 线上 Bug 占总 Bug 的比例 | 线上 Bug 数 / (线上 + 测试 Bug 数) × 100% | ≤ 10% | 手动录入 | 每月 |
| R4 | 回归缺陷率 | 修复一个 Bug 引入新 Bug 的比例 | 回归 Bug 数 / 修复 Bug 数 × 100% | ≤ 5% | 手动录入 | 每月 |

### 指标详解

**R1 线上 Bug 数**
- 目的：衡量最终交付质量的最直接指标
- 分类：P0（崩溃）/ P1（功能不可用）/ P2（体验问题）
- 数据来源：Bug 跟踪系统（Jira/飞书项目）

**R2 缺陷密度**
- 目的：消除代码规模影响，跨项目对比质量
- 公式：Bug 数 / 代码行数 × 1000（每千行代码的 Bug 数）
- 阈值：> 2 说明质量需要改善

**R3 漏测率**
- 目的：衡量测试有效性，漏测率高说明测试用例覆盖不足
- 公式：线上 Bug / (线上 Bug + 测试阶段发现的 Bug)
- 阈值：> 10% 说明测试策略需要调整

**R4 回归缺陷率**
- 目的：衡量修复质量，高回归率说明修复不彻底
- 公式：回归 Bug / 修复 Bug
- 阈值：> 5% 说明需要加强回归测试

## 四、效率指标（4 个）

> 效率指标衡量「效率高不高」，反映研发流程的效率。

| # | 指标名称 | 定义 | 计算公式 | 目标值 | 采集方式 | 频率 |
|---|---------|------|----------|--------|---------|------|
| E1 | PR 流水线时长 | PR 级 CI 的平均执行时间 | 总执行时间 / 执行次数 | ≤ 10 分钟 | GitHub Actions API | 每周 |
| E2 | 全量回归时长 | 每日级全量回归的执行时间 | daily workflow 执行时长 | ≤ 30 分钟 | GitHub Actions API | 每日 |
| E3 | 用例维护成本 | 每人维护的用例数量 | 总用例数 / 测试人数 | 递增趋势 | 手动统计 | 每月 |
| E4 | 精准测试节省时间 | 精准测试相比全量节省的时间 | 1 - 精准耗时 / 全量耗时 | ≥ 40% | 评估脚本 | 每次 PR |

### 指标详解

**E1 PR 流水线时长**
- 目的：PR 等待时间是研发效率的关键瓶颈
- 采集：GitHub Actions API 获取 workflow run 的 `updated_at - run_started_at`
- 阈值：> 10 分钟触发优化（并行化 / 缓存 / 精准测试）

**E2 全量回归时长**
- 目的：每日回归的执行时间影响每日发版节奏
- 采集：daily-pipeline.yml 的执行时长
- 阈值：> 30 分钟触发优化（拆分 job / 并行化）

**E3 用例维护成本**
- 目的：监控用例维护负担，人均用例数过高说明需要自动化
- 采集：统计 tests/ 目录下的测试函数数量
- 阈值：趋势上升过快需要评估投入产出比

**E4 精准测试节省时间**
- 目的：衡量精准测试的 ROI
- 采集：evaluate_precision.py 脚本输出
- 阈值：< 40% 说明精准测试规则需要优化

## 五、指标关系图

```
                    ┌─────────────────────────────────┐
                    │         过程指标（P1-P6）         │
                    │  通过率 / 覆盖率 / 门禁 / 扫描    │
                    └──────────────┬──────────────────┘
                                   │ 影响
                                   ▼
                    ┌─────────────────────────────────┐
                    │         结果指标（R1-R4）         │
                    │  线上Bug / 缺陷密度 / 漏测率      │
                    └──────────────┬──────────────────┘
                                   │ 反馈优化
                                   ▼
                    ┌─────────────────────────────────┐
                    │         效率指标（E1-E4）         │
                    │  CI时长 / 回归时长 / 精准节省     │
                    └─────────────────────────────────┘
```

### 指标间关键关系

| 关系 | 说明 |
|------|------|
| P3 覆盖率 ↑ → R3 漏测率 ↓ | 覆盖率提升，漏测率应下降 |
| P1 通过率 ↓ → R1 线上Bug ↑ | 通过率下降，线上 Bug 可能增加 |
| P4 门禁阻断率 → R4 回归缺陷率 | 门禁拦截的问题不会变成线上回归 |
| E4 精准节省时间 → E1 PR时长 ↓ | 精准测试减少用例，PR 时长缩短 |
| P5 告警数 ↓ → R2 缺陷密度 ↓ | 代码质量提升，缺陷密度下降 |
| E1 PR时长 ↑ → P1 通过率 ↓ | PR 太慢，开发者倾向跳过测试 |

## 七、指标演进路线图

### V1（当前 - 第3周）

| 优先级 | 指标 | 说明 |
|--------|------|------|
| P0 | P1 通过率 | 从 junit XML 自动采集 |
| P0 | P3 覆盖率 | 从 coverage.xml 自动采集 |
| P0 | E1 PR 时长 | 从 GitHub Actions API 采集 |
| P0 | E2 回归时长 | 从 GitHub Actions API 采集 |
| P1 | P6 安全问题 | 从 bandit 报告采集 |
| P1 | E4 精准节省 | 从 evaluate_precision.py 采集 |

| 优先级 | 指标 | 说明 |

| 优先级 | 指标 | 说明 |

## 八、采集方式汇总

| 采集方式 | 覆盖指标 | 自动化程度 |
|----------|---------|-----------|
| junit XML 解析 | P1, P2 | 全自动 |
| coverage.xml 解析 | P3 | 全自动 |
| bandit 报告 | P6 | 全自动 |
| flake8/pylint 输出 | P5 | 全自动 |
| GitHub Actions API | E1, E2, P4 | 全自动 |
| evaluate_precision.py | E4 | 全自动 |
| Bug 跟踪系统 | R1, R3 | 半自动 |
| 手动录入 | R2, R4, E3 | 手动 |

> V1 版本 6 个指标全部可从 CI 自动采集，无需手动录入。
