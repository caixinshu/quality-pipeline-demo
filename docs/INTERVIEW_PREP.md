# 面试话术准备

> 项目一：质量流水线与 CI/CD 平台 · 面试素材

---

## 一、30 秒电梯演讲

> "我独立搭建了一套四层 CI/CD 质量流水线，从代码提交到 UI 验证全链路自动化。包含三条质量门禁、精准测试、质量看板和 UI 自动化，PR 等待时间优化了 37%，覆盖率从 40% 提升到 70%+。"

**要点**：一句话说清项目价值（全链路自动化）+ 量化成果（37% 优化、覆盖率提升）+ 你的角色（独立完成）。

---

## 二、3 分钟深度介绍

### 第 1 分钟：项目背景 + 架构

"这个项目解决的核心问题是：如何让代码从提交到上线，全程自动化质量保障。

我设计了四层流水线：
- **提交级**：开发每次 push 触发，跑 lint + 单元测试，30 秒内反馈
- **合并级**：PR 触发，跑冒烟测试 + 精准测试 + UI 冒烟，5 分钟内完成
- **每日级**：cron 触发，跑全量回归 + 全量扫描 + 三浏览器 UI 测试
- **发布级**：tag 触发，跑全量验证 + 人工审批后发布

四层之间不重复，每层只做该做的事。"

### 第 2 分钟：核心难点 + 解决方案

"最大的难点有三个：

**第一，PR 等待时间过长**。原来所有测试串行跑一遍要 8 分钟。我分析了各 job 耗时，发现串行执行是瓶颈。改为并行 + 五层缓存（pip/Docker/Playwright/Allure/npm），优化到 5 分钟，节省 37%。

**第二，测试执行量太大**。每次 PR 跑全部测试浪费资源。我写了精准测试脚本，基于 git diff 分析变更文件，正则匹配关联测试用例，只跑相关的。召回率 80%+，执行量减少 50%。

**第三，UI 测试跨浏览器兼容**。接入 Playwright，配置 Chromium/Firefox/WebKit 三浏览器并行矩阵。失败时自动保留 Trace 文件，可以下载用 Trace Viewer 回放每一步操作。"

### 第 3 分钟：效果数据 + 总结

"最终效果：
- PR 流水线 8min → 5min（-37%）
- 覆盖率 40% → 70%+
- 精准测试召回率 80%+，执行量减少 50%
- 14 个质量指标在线看板
- 三浏览器并行 UI 测试

这个项目让我从 L3（能写测试）迈向 L4（能设计质量体系），最大的收获是学会了用分层和投入产出比的思维来做质量工程。"

## 三、预判面试官问题

### Q1：四层流水线为什么要分层？

**A**：不同场景需求不同——提交要快（30 秒反馈），合并要全（PR 是最后一道防线），每日要深（全量回归发现隐藏问题），发布要稳（人工审批）。分层让每层只做该做的事，避免过度设计。

如果只有一层流水线，要么太快（覆盖不足），要么太慢（开发体验差）。分层是速度和质量的平衡。

### Q2：精准测试准确率只有 80%，为什么不继续优化？

**A**：L1 版（文件匹配）准确率上限就是 70-80%。要提升到 90%+ 需要 L2（覆盖率映射）或 L3（调用链分析），投入产出比不划算。当前用冒烟集兜底，精准测试减少执行量，冒烟集保底覆盖，组合起来满足需求。

这是一个工程取舍——不是追求技术完美，而是追求投入产出比最优。

### Q3：质量门禁会不会太严影响开发效率？

**A**：门禁分级设计——严重问题（如 HIGH 级安全漏洞）阻断，一般问题（如代码风格）只警告。灰度上线，先用 `continue-on-error: true` 只看不阻断，告警降下来后再开启阻断。和团队对齐规则，不是单方面说了算。

门禁的目的不是阻断开发，而是提高代码质量底线。

### Q4：为什么选 Playwright 不选 Selenium？

**A**：Playwright 原生支持多浏览器、自动等待、Trace 调试，API 更现代，CI 集成更简单。Selenium 也能用，但 Playwright 在 DX（开发体验）上好太多。

具体来说：
- Playwright 的 `auto-wait` 省掉了大量 `WebDriverWait` 样板代码
- Trace Viewer 是 Selenium 没有的，调试失败用例效率提升很大
- Playwright 的 Docker 镜像开箱即用，Selenium Grid 搭建更复杂

### Q5：覆盖率 70% 够用吗？为什么不追求 100%？

**A**：70% 是投入产出比最优点。从 40% 到 70% 投入不大，边际收益高。从 70% 到 100% 投入急剧增加，但很多是在测 getter/setter 这类无意义代码。古德哈特定律提醒我们：覆盖率不能作为唯一指标。

我更关注测试质量——是否覆盖了核心业务路径、异常分支、边界条件，而不是单纯追数字。

### Q6：GitHub Actions 为什么不用 Jenkins？

**A**：三个原因：
1. **零运维**：Jenkins 需要自己维护服务器，GitHub Actions 是 SaaS
2. **原生集成**：和 GitHub 仓库无缝连接，PR 触发、分支保护都是原生支持
3. **免费额度**：公开仓库免费无限分钟，私有仓库也有 2000 分钟/月

Jenkins 的优势是插件生态和定制能力，但对于这个项目的规模，GitHub Actions 是最优选。

### Q7：你的质量看板和 Grafana 有什么区别？

**A**：Grafana 是重量级方案，需要数据源（Prometheus/InfluxDB）+ 服务器。我的看板是轻量级方案——ECharts + 静态 JSON + GitHub Pages，零运维零成本。

看板定位是"CI 质量数据可视化"，不是"实时监控系统"。数据每天更新一次就够了，不需要实时。如果要实时监控，那确实应该用 Grafana。

### Q8：如果让你重新做这个项目，你会怎么改？

**A**：三个改进方向：
1. **精准测试升级到 L2**：用 coverage map 替代文件匹配，召回率提到 90%+
2. **接入 Allure Server**：持久化测试报告，不依赖 artifact 14 天过期
3. **加性能测试**：用 k6 做接口性能基线测试，在每日级流水线中跑

最大的遗憾是 UI 测试覆盖不够，只有 10+ 条。如果有更多时间，会扩展到完整用户旅程测试。

## 四、技术对比话术

### Playwright vs Selenium

| 维度 | Playwright | Selenium |
|------|-----------|----------|
| 多浏览器 | 原生支持 | 需要 WebDriver |
| 自动等待 | 内置 | 手动 WebDriverWait |
| Trace 调试 | 内置 Trace Viewer | 无 |
| CI 集成 | Docker 镜像开箱即用 | Selenium Grid 较复杂 |
| API 风格 | 现代 async/await | 回调式 |
| 速度 | 快（CDP 协议） | 慢（HTTP 协议） |

### GitHub Actions vs Jenkins

| 维度 | GitHub Actions | Jenkins |
|------|---------------|---------|
| 运维 | 零运维（SaaS） | 需要维护服务器 |
| 集成 | GitHub 原生 | 需要插件 |
| 成本 | 公开仓库免费 | 服务器成本 |
| 定制 | YAML 声明式 | Groovy 脚本式 |
| 生态 | Marketplace | 插件市场更大 |

### 精准测试 L1 vs L2 vs L3

| 级别 | 方法 | 召回率 | 投入 |
|------|------|--------|------|
| L1 | 文件匹配 | 70-80% | 1 天 |
| L2 | 覆盖率映射 | 85-90% | 1 周 |
| L3 | 调用链分析 | 95%+ | 1 月+ |

## 五、面试注意事项

1. **用数据说话**：不说"优化了很多"，说"从 8min 优化到 5min，节省 37%"
2. **讲故事不是念简历**：用"问题 → 方案 → 效果"的结构
3. **诚实面对不足**：精准测试 80% 就是 80%，不说 95%
4. **展示思考过程**：不只说做了什么，还说为什么这么做、考虑了什么替代方案
5. **准备反问问题**："贵团队的 CI/CD 流水线是什么架构？质量门禁怎么设计的？"
