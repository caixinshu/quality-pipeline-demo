# 下周预习：精准测试（Precision Testing）

## 一、什么是精准测试

精准测试的核心思想：**只运行与代码变更相关的测试用例**，而不是每次都跑全量。

### 传统全量回归的问题
- 1000 条测试跑 30 分钟，但只有 10 条和本次改动有关
- 浪费 CI 资源，降低反馈速度
- 开发者等待时间过长

### 精准测试的优势
- 只跑相关用例，从 30 分钟降到 2 分钟
- 快速反馈，提高开发效率
- 节省 CI 资源

## 二、工业界实现方案

### 方案 1：git diff + 代码映射（轻量级）

```bash
# 获取本次变更的文件
git diff --name-only HEAD~1 HEAD

# 输出示例：
# app/main.py
# app/models.py

# 根据变更文件找到对应的测试
pytest tests/test_api.py -v  # 只跑 main.py 对应的测试
```

### 方案 2：覆盖率追踪（中量级）

1. 首次运行全量测试，收集每条用例覆盖了哪些代码行
2. 建立「测试用例 → 代码行」映射表
3. 当某行代码变更时，查找映射表，只运行相关用例

### 方案 3：AST 分析（重量级）

1. 解析代码 AST（抽象语法树），建立函数/类调用关系图
2. 当函数 A 变更时，找到所有调用 A 的函数 B、C、D
3. 运行覆盖了 B、C、D 的测试用例

## 三、git diff 高级用法

```bash
# 只看变更的文件名
git diff --name-only

# 比较两个 commit 之间的差异
git diff commit1..commit2 --name-only

# 只看变更的行（统计）
git diff --stat

# 导出变更文件列表
git diff --name-only HEAD~1 HEAD > changed_files.txt
```

## 四、代码覆盖率追踪原理

```
测试执行 → 生成 .coverage 文件 → 记录每行代码被哪些测试覆盖
                                    ↓
代码变更 → git diff 找到变更行 → 查映射表 → 找到相关测试 → 只跑这些测试
```

## 五、思考题

如果让你来设计精准测试，你会怎么做？

参考思路：
1. **第一步**：先实现 git diff 级别的精准测试（最简单）
2. **第二步**：收集覆盖率数据，建立映射表
3. **第三步**：在 CI 中实现自动化的「变更分析 → 用例筛选 → 定向执行」
4. **第四步**：兜底机制 — 精准测试 + 每日全量回归双保险
